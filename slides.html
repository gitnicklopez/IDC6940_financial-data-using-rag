A Capstone Project in Data Science

July 28, 2026

The Problem: Tiny AI Mistakes, Big Consequences

This image was generated using Gemini.

Why This Happens

  • Retrieval-Augmented Generation (RAG) retrieves relevant passages from a document library, then grounds an LLM’s answer in that material.
  • Naive RAG works well for narrative, text-heavy tasks (compliance, audit reporting).
  • Standard RAG pipelines read documents linearly — great for prose, but potentially bad for structured tables.

Two potential failure points:

  • Context Loss — chunking separates numbers from their row/column labels.
  • Formatting Issues — linear reading jumbles rows and columns together.

Methodology

We compare two RAG architectures on a corpus of real financial reports, and introduce a new metric — Numerical Atomic Verification (NAV) — to explicitly measure numerical fidelity.

  • Architecture A — Naive RAG: Comparitive baseline that uses linear PDF text extraction + basic semantic search.
  • Architecture B — Table-Aware Dual-Branch RAG: Proposed pipeline that separates narrative text from tables, preserves row/column lineage, and reconstructs full tables at query time.

Architecture A: Naive RAG

  1. Ingestion — pdfplumber reads text sequentially, ignoring table bounding boxes. A table row becomes one flat string with no link between headers and values.
  2. Indexing — RecursiveCharacterTextSplitter (chunk size 512, overlap 50), split on space/character only — often cuts tables apart mid-row.
  3. Retrieval — query + corpus normalized (tokenize()), ranked with BM25Okapi (top-5 chunks).
  4. Generation — top chunks + query sent to Gemini 3.5-flash, instructed to answer only from provided context.

Architecture B: Table-Aware Dual-Branch RAG

  1. Bifurcated Ingestion — camelot extracts tables, pdfplumber extracts narrative text; headers consolidated, data cleansed.
  2. Narrative Chunking — same 512/50 sizing as A, but splits on paragraph/sentence boundaries first and preserves page metadata.
  3. SRSE Row Chunking — every table row becomes one Single-Row Single-Embedding string
  4. Hybrid Index — narrative text and table rows kept in separate, metadata-rich lists.
  5. Dual-Channel Retrieval + Reconstruction — searches both branches with BM25; a matched row triggers full-table reconstruction before generation.

  • Ground truth defines expected file, page, and exact numeric answer for each question.

Indexing Granularity: A vs. B

Results: Overall Performance

Note: PageHit Recall/Precision and CEA aren’t computable for Architecture A — its flat chunking discards page/table structure entirely.

Results: The Surprise

  • PageHit Recall (B) is high — relevant chunks are in the context window.
  • But PageHit Precision ≈ 0.57 — correct chunks often rank 2nd–3rd out of 5, adding noise.
  • CEA = 0.93 — when Architecture B retrieves the right chunk, the LLM answers correctly almost every time.
  • Yet on NAV Accuracy, the primary metric, Architecture A outperformed Architecture B by ~7% (4 questions) — the opposite of what we expected.

Results by Question Tier

Naive RAG (A) outperformed Table-Aware RAG (B) across all three tiers — even Tier 2 (table extraction), where B was expected to win.

Why Did the “Better” Method Lose?

  • Not a generation problem — Architecture B is 93% accurate when it finds the right data (CEA).
  • It’s a retrieval problem: breaking tables into single-row SRSE chunks strips out broader context (report year, company name, table title).
  • BM25 keyword search missed the correct row ~25% of the time because those keywords weren’t present in the isolated row text.
  • Core trade-off: finer-grained chunking preserves structure but makes chunks harder to find with keyword-based search.

Key Findings

  1. Unexpected result: the simpler baseline (Naive RAG) beat the custom table-aware pipeline on numerical accuracy, across every question tier.
  2. The search problem: Table-Aware RAG’s row-level chunks lack contextual keywords, causing ~25% retrieval misses.
  3. Successful generation: once the correct data is retrieved, Table-Aware RAG is highly accurate (93% CEA) — the generation step is sound.

Implications & Next Steps

  • Metadata Enrichment — prepend global context (reporting year, table title) to each row chunk before indexing, so macro-queries can still find it.
  • Hybrid / Dense Retrieval — combine BM25 with dense vector embeddings + re-ranking to catch semantic (not just keyword) matches.
  • Multi-Stage (“Parent-Child”) Search — first locate the right page, then the right table, then the right row — narrowing top-down instead of searching flat row indexes.

Conclusion

  • Table-Aware Dual-Branch RAG (Architecture B) preserves table structure and is highly accurate once it finds the right evidence.
  • But structure preservation alone isn’t enough — retrieval must be re-engineered to work with finer-grained, context-poor chunks.
  • Building reliable financial AI requires balancing structural fidelity with searchability — a core challenge for trustworthy, accurate AI in high-stakes domains.
